# Shared SHA-256

Accepted (chronium, 2026-10-25): one userland static library, exported with the
SDK, supplies incremental SHA-256 and a shared compression interface. It has
no entropy, clock, allocator or capability requirement. Caller-owned contexts
are independent; one context cannot be updated concurrently.

`sha256.h` defines `sha256_context`, `sha256_init`, `sha256_update` and
`sha256_finish`. Initialize before use. A zero-length update permits a null
input. Inputs and outputs must not overlap the context. Updates reject byte
counts beyond SHA-256's 64-bit bit-length field and poison the context on a
bad buffer or overlength; successful finalization clears the context and
prevents reuse until initialization. A null digest output also poisons it.
Finish returns the 32 raw digest bytes. No hexadecimal or FILE policy lives
in the library. Link `-lsha256` before the normal runtime libraries.

`sha256_compress` applies complete 64-byte blocks to eight initialized
host-endian state words, without initialization or padding. It exists for
existing SHA-224/SHA-256 providers; SHA-224 uses the same compression primitive
with different initial state and output truncation. The state and input must
not overlap; zero blocks permit a null input.

The portable compression core is extracted from TF-PSA-Crypto 1.1.1
`a0632be94d883daa0295ac1eabf70359ad94f91b`, using its Apache-2.0 option.
Its provenance and full licence are exported in the SDK. The x86 backend
requires CPUID SHA, SSSE3 and SSE4.1, selects once per process without a thread
service, and uses only legacy SSE SHA-NI encodings. Backend selection and ISA
code live under `libsha256/arch/x86_64`; the streaming code is architecture
independent. Builds explicitly disable AVX; disassembly checks are part of
qualification. No kernel FPU/state change is required.

Accepted (chronium, 2026-10-25): kernel and Go remain unchanged here. Standard
Go SHA-256/SHA-1 fast paths currently require AVX; Caelum preserves x87/SSE
with FXSAVE and disables OSXSAVE. General XSAVE/AVX support is a separate task
with llvmpipe. Git's collision-detecting sha1cd already has a legacy-SSE SHA-NI
path; its collision protection remains enabled. LLVM, WPA and host Python/
OpenSSL retain their existing implementations.

Payload hashing in pkg, installer/boot handoff, xfer, Lua, sbase and host
Remote/GDB uses the library. Mbed TLS SHA-224/SHA-256 compression uses the same
engine, retaining its existing framing and SHA-224 truncation. The migrations
preserve limits, identities, comparisons and durability ordering. Certificate
and signature operations retain PSA initialization and their existing authority
requirements. Host tools build the same sources into a host static archive;
non-x86 hosts use portable dispatch. Full notices accompany the SDK, native
packages and host tools.

## Baseline and qualification

The pre-change four-vCPU KVM baseline hashes 64 MiB three times: raw scalar
Mbed memory hashing median 372.1 MiB/s (367.9–372.7); the existing copying PSA
wrapper 199.8 (199.4–223.6); RAM FILE read/byte scan 1976.5 (1943.4–1978.9).
These are nested-VM observations, not native throughput. Supplied native vela
phase traces after HWP show archive verification 3.71 s for 268 MiB and
extraction 5.31 s for 1242 files; the captured command later refused a missing
pyxis-dev dependency, so these are phase observations, not activation proof.

Host GCC16 and Clang23 checks of the x86 backend matched 609 independently
checked compression/streaming cases each. The complete library also matched
182 hashlib streaming combinations across empty input, padding/block
boundaries, split updates and larger input, with invalid-buffer, length-bound,
finalization and reset behavior checked. Optimized host disassembly contains
SHA-NI and legacy SSE only. Native target archive builds with the existing
Clang23 SDK; QEMU portable/accelerated dispatch, consumer checks and the matched
native vela packet are recorded with the consumer delivery.

The investigation and private raw evidence are at
`/shared/present/sha256/REPORT.md`. No SHA-NI native throughput or speedup is
claimed before the scheduled native comparison.

A matched four-vCPU KVM run (`max,+invtsc`, 4 GiB, Clang 23, unchanged
`e57d9701e051` kernel/ABI 0.0.8, RAM FILE, three repetitions of 64 MiB) measured
memory hash at 16 KiB caller updates: before PSA wrapper median 382.3 MiB/s
(381.2–385.6), shared library 2206.4 (2201.4–2210.8). Read-and-hash medians were
326.6 (325.4–326.7) and 1203.1 (1199.8–1207.9). Both link the same C runtime;
only the hash consumer/provider differ. These numbers supersede the initial
unmatched-library baseline for speedup comparisons. Target monotonic intervals
exclude allocation, data preparation and output. All complete digests matched;
this is nested-VM, not native performance.

The prepared vela comparison uses the existing HWP live PXE environment and a
RAM package pool. It alternates old/new/old/new helpers and pkg clients with
four fresh package versions of an identical 268 MiB/1242-file payload. Each
checks memory, FILE scan/read-and-hash, archive verification, fresh extraction
and the selected set. Package phase boundaries observed over Remote include
transport/scheduling delay; they are not target-internal phase timings. The
packet and machine-readable collector are in `/shared/present/sha256/vela-check/`.
No native result is claimed until the orchestrator runs it.
